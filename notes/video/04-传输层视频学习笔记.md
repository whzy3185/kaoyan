## 一、视频主线

TCP 首部字段 → TCP 序号/确认号 → 三次握手 → 四次挥手/TIME-WAIT → 流量控制与零窗口 → 拥塞控制 → 408 真题串讲 → UDP → 复用/分用 → UDP 校验和。

## 二、TCP 首部

视频逐字段讲解 TCP 首部。

### 源端口与目的端口

- 各 16 bit。
- 用于标识通信进程。

### 序号 seq

- 32 bit。
- TCP 面向字节流，因此序号编号的是**字节**。
- 某报文段序号表示该报文段中第一个数据字节的编号。

若一个 TCP 段：

- seq = 200
- 携带 300B 数据

则后续连续段的序号从：

$$200+300=500$$

开始。

### 确认号 ack

- 32 bit。
- 表示“期望收到对方的下一个字节序号”。

所以累计确认关系是：

$$ack=	ext{已连续正确收到的最后一个字节序号}+1$$

### 数据偏移

- 4 bit。
- 表示 TCP 首部长度。
- 单位为 4B。
- 最大 TCP 首部长度为 60B。

### 控制位

视频画面中明确讲解：

- URG
- ACK
- PSH
- RST
- SYN
- FIN

其中：

- SYN：连接建立。
- FIN：连接释放。
- ACK：确认号有效。
- RST：异常复位连接。

### 窗口

- 16 bit。
- 是接收方向发送方通告的接收窗口。
- 用于 TCP 流量控制。

### 校验和

覆盖 TCP 首部、数据以及计算时加入的伪首部。

### 紧急指针

仅在 URG=1 时有意义，用于指出紧急数据位置。

## 三、TCP 序号与确认号的统一判断

后续做题固定使用：

1. 先看该段的 seq。
2. 看该段携带多少字节。
3. 对方如果连续正确收到，则：

$$ack=seq+	ext{数据长度}$$

4. SYN 和 FIN 虽然可以不携带应用数据，但各自会占用一个序号。

这是三次握手、四次挥手和综合题中的核心。

## 四、TCP 三次握手

视频使用状态图讲：

### 第一次握手

客户端主动发出 SYN：

- SYN=1
- seq=x

SYN 会消耗一个序号。

### 第二次握手

服务器确认并同步自己的初始序号：

- SYN=1
- ACK=1
- seq=y
- ack=x+1

### 第三次握手

客户端确认服务器：

- ACK=1
- seq=x+1
- ack=y+1

第三次握手的纯 ACK 本身如果不携带数据，不额外消耗序号。

视频通过 2011 等真题反复训练“看 SYN/ACK 与 seq/ack 是否一致”。

## 五、为什么需要三次握手

视频沿用“失效的旧连接请求迟到”这一思路：

如果只两次握手，服务器可能对一个已经失效的旧 SYN 建立连接并持续等待数据。

第三次握手让服务器确认：客户端确实收到了本次连接的应答，并愿意建立这条连接。

## 六、TCP 四次挥手

视频画出主动关闭方与被动关闭方状态转换。

典型过程：

1. 主动方发送 FIN。
2. 被动方 ACK。
3. 被动方处理完剩余数据后发送 FIN。
4. 主动方 ACK。

因为 TCP 是全双工，两方向数据流需要分别关闭，所以通常表现为四次交互。

### TIME-WAIT

主动关闭方在最后 ACK 后进入 TIME-WAIT。

视频板书强调等待：

$$2MSL$$

原因与旧报文段消失、确保最后 ACK 有机会重传有关。

## 七、TCP 流量控制

TCP 通过接收方通告的接收窗口 (rwnd) 限制发送方。

发送窗口受多个因素共同约束，但从流量控制角度看，不能超过对方当前可接收空间。

### 零窗口

当接收方通告窗口为 0 时，发送方不能继续正常发送数据。

视频提到零窗口探测/持续计时器思想：发送方不能永久沉默，需要周期性探测对方窗口是否重新打开。

## 八、TCP 拥塞控制

视频把拥塞控制流程整理为慢开始、拥塞避免、超时处理、快重传和快恢复。

### 初始拥塞窗口

视频所用教学模型中常从：

$$cwnd=1MSS$$

开始。

### 慢开始

每经过一个 RTT，拥塞窗口近似翻倍：

$$1,2,4,8,ldots$$

当 (cwnd) 达到慢开始门限 (ssthresh) 后进入拥塞避免。

### 拥塞避免

按视频讲解，每经过一个 RTT 约增加 1 MSS。

### 超时

若发生重传超时：

$$ssthresh=rac{cwnd}{2}$$

随后把拥塞窗口降到较小值，并重新执行慢开始。

### 快重传

发送方连续收到 **3 个重复 ACK** 后，不等超时计时器到期，立即重传疑似丢失报文段。

### 快恢复

视频把快重传与快恢复配套讲解，核心是避免在仅有个别报文段丢失时完全退回最初的慢开始状态。

## 九、拥塞窗口与发送窗口

真题中常同时出现：

- (cwnd)：拥塞控制限制
- (rwnd)：接收方流量控制限制

实际可发送的数据量需要同时满足两者，因此做题时要检查：

$$	ext{发送窗口}le min(cwnd,rwnd)$$

再扣除已经发送但尚未确认的数据。

## 十、TCP 高频真题判断链

### 序号确认号

**seq + 有效数据长度 → 对方 ack**

### 三次握手

- SYN 消耗 1 个序号。
- 第二次必须 SYN=1、ACK=1。
- 确认号必须是对方 SYN 序号 + 1。

### 四次挥手

- FIN 消耗 1 个序号。
- 主动关闭方最后进入 TIME-WAIT。
- TIME-WAIT = 2MSL。

### 拥塞控制

1. 先标出当前 (cwnd)。
2. 判断当前处于慢开始还是拥塞避免。
3. 判断事件是正常 ACK、超时还是 3 个重复 ACK。
4. 再更新 (ssthresh) 与 (cwnd)。

## 十一、UDP

视频后半段切换到 UDP。

UDP 主要特点：

- 无连接。
- 面向报文。
- 首部固定 8B。
- 不提供 TCP 那样的可靠传输、流量控制和拥塞控制机制。

### UDP 首部

四个 16 bit 字段：

- 源端口
- 目的端口
- 长度
- 校验和

总首部长度：

$$4	imes2B=8B$$

### 长度字段

表示：

$$	ext{UDP首部}+	ext{UDP数据}$$

## 十二、UDP 复用与分用

发送端多个应用进程的数据可由 UDP 复用后向下交给 IP。

接收端根据 UDP 首部中的端口号，把报文交给对应进程。

做题时重点关注：

- 目的端口用于接收端分用。
- 源端口用于返回响应等场景。

## 十三、UDP 校验和

视频末尾通过伪首部图讲解 UDP 校验。

计算时不仅有：

- UDP 首部
- UDP 数据

还需要加入 **伪首部**。

伪首部参与校验计算，但不会真正作为 UDP 用户数据报的一部分传输给应用层。

如果数据长度不是 16 bit 的整数倍，计算时需要按规则补 0。
